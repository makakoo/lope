# S2 evidence — Tier 2 supervised runtime and completion policy
generated 2026-11-07T17:03:59Z

## Design (as built)
- Parent (lope_runtime::call::run_subprocess_group) -> supervisor process (the lope binary
  re-executed with argv0 'lope-supervisor'; no CLI surface added) -> provider in its own
  session/process group. Control pipe EOF = owner died -> supervisor SIGKILLs the group
  (tested). Supervisor SIGTERM handler kills the group syscall-only, as in Python.
- Event-driven: reader/writer/waitpid threads feed a channel; no sleep-polling except the
  bounded post-exit group confirmation (killpg(pgid,0) with 5->50 ms back-off) (NFR3).
- Completion policy = Python's fail-closed policy with a 2.0 s cleanup budget
  (LOPE_CLEANUP_BUDGET_SECONDS, additive). Post-exit: probe group; if non-empty TERM,
  200 ms grace, KILL, confirm. Result strings identical to supervisor.py.
- The parent passes its absolute deadline (spec key deadline_at) so the supervisor
  classifies provider_timeout itself; the parent's reserve is budget+0.5 s (Python: 1.0 s
  for a 0.7 s budget).
- FR12: provider_timeout / cancelled write a 0600 JSON sidecar under runs/diag/
  (outside runs/work/<run>, which Python's closeout requires to be empty), with bytes per
  stream, seconds since last byte, leader alive + ps state, group probe and a <=4 KiB
  redacted stderr tail. The call manifest gets diag_path (A4 proved extra fields are
  tolerated). Pruned after 7 days (lope_runtime::diag::prune).

Interpretation: on this Intel Mac the confirmation itself takes ~5-8 ms once launchd
reaps the killed children; the earlier A5 runs at load average ~60-100 showed p95 call
wall time 0.1 s and zero false UNVERIFIED. 2.0 s keeps >200x headroom over the measured
p99 while bounding the worst case. Python's 0.7 s budget also passed at load ~15; the D1
false-UNVERIFIED pattern needs heavy load, which the larger budget absorbs.
